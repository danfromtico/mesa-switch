# 旧式 SEQUENTIAL 首次 Present 的同包回执

使用旧式窗口正常出现时的短采集窗口。复用项目的 DxgKrnl ETW、GM20B DMA 诊断事件和独立控制端接收器。正式 KMD 能提供 Windows 侧时间线。KMD 入返及 GPU 围栏读回要使用已有的诊断候选 `ef790ec9`，该驱动曾在 94004 一次性许可下校准。每次以实际加载组件及其完整哈希为准。

## 同次提交的关联

| 步骤 | 证据 | 同包条件与覆盖 |
| --- | --- | --- |
| Windows 队列与调度 | DxgKrnl 178.1 入队和 175.1 提交 | 同启动、适配器 LUID、节点、上下文生命期，匹配 `hContext`、队列序号及对象 `pQueuePacket`。每个 `uliSubmissionId` 是一次独立的尝试。系统线程 PID/TID 是发事件的线程。DWM 所有权从设备与上下文取证。 |
| 选择提交分支 | DxgKrnl 105/106 的 5063 区间 | 只在同调度线程唯一包围 KMD 入返并排除相邻 175 时关联。函数编号单独出现时保留缺口。 |
| KMD 进入、准入及返回 | 项目 provider `c27c1f9b-62e8-4e21-b29b-6bb2d585c6d0` 的 7.2，阶段 1、2、5 | 用同启动的 Windows 433 建立 `hContext` 和私有 KMD 上下文的映射，再核对适配器、提交 fence、DMA 字节、提交线程和调用区间。阶段 5 记录实际返回状态。工作线程可能早于返回继续执行。 |
| 发布及 GPU 完成 | 7.2 阶段 3、4 | 阶段 3 观察到 GPFIFO 发布，实际 GPU 开始时刻仍缺直接事件。阶段 4 发生在命令完成字读回成功之后，可证实读回的 GPU 完成，完成的精确硬件时刻仍未知。 |
| Windows 收到驱动通知并处理完成 | DxgKrnl 177.1 和 176.0 | 分别读回通知与 Windows 的 DMA 完成处理。匹配上下文、同一次 DMA 完成号、队列序号、正常通知类型、无页故障及 `bPreempted=0`。驱动通知单独留下时，GPU 完成读回和退役各按其证据记录。 |
| Windows 队列退役 | DxgKrnl 180.1 | 180 的载荷没有 DMA 提交号。须以同一 178 的队列对象及队列序号、上下文生命期和唯一的非抢占 176 来归属。存在另一尝试或对象复用的歧义时保留未知。 |
| 系统结果 | 下一次启动的原始系统事件、启停时刻及已有恢复回执 | 记录实际启动和异常关机，首个异常或复位时刻只采用可独立定位的事件。 |

抢占后的 175 另开一条尝试。可回读的抢占完成按实际状态报告。即使几次尝试共用相同队列对象，完成号和回执也各自归属。DWM 信号、等待和后续呈现的选择事件按各自包记录。用应用日志或 DXGI 42/43 确定首次 Present 的线程和 QPC 范围。要把 DWM 包归到该窗口，还需同次窗口及组成链证据。

## 两个独立时钟与落盘

- 开始前在独立接收端保存本轮唯一标识、Windows 启动、系统与驱动组件哈希、进程、适配器、上下文映射及 QPC 频率。地址、序号和计数只在绑定的启动、捕获窗口和对象生命期内使用。现有实时流传输 175、5063、KMD 7、177、176 和 180。队列 178 与上下文 433 须另存同启动原始事件，现有实时流缺它们的独立落盘保证。
- 源事件的 QPC 与采集回调的 QPC 在同一 Windows 时间基准。独立控制端给每条收取和 `fsync` 返回写入本机单调钟和 UTC。Windows 收到 `ACK n` 后记录自己的 QPC。可用回调与 ACK 的顺序约束落盘位置。跨设备时点不直接相减。
- 接收器的 `wire.jsonl` 在控制端创建。保留原文件并在新进程用 [recover_dma_receipts.py](../../tools/recover_dma_receipts.py) 读取。单独的 EVENT 是已收取并可读回的记录，完整的 `fsynced` 是接收端完成前一条 EVENT 同步写入的记录，`PERSISTED` 是 Windows 收到 ACK 的回执。报告三者的计数及每个阶段的原始载荷。没有完整换行的尾记录保持未确认。格式错误的完整行会终止读取，已验证前缀仍可导出。
- 正常收尾时读回原生 ETW 停止状态、事件丢失、实时缓冲丢失和文件缓冲丢失。无 END 时最终丢失计数未知。即使收到带零丢失的 END，也同时核对上限、ACK、写入和传输错误。未知阶段可能发生在 ETW、回调、传输或落盘覆盖之外。

## 本轮准备状态

控制端恢复读取通过了真实进程中断的本地验证。回放的事件字节和源 QPC 来自 94004 的已有正常 DWM DMA，模拟的采集和 ACK 时钟单独标记。原场景和正常窗口均未重跑。现场尚未布防。

现有扩容实时收集器的上限为 8192 条，最长窗口 12 秒。旧版在桌面后台约一秒触达 4096 条，8192 版仅有本地压力验证。现有工具还需要同启动的队列和上下文原始回执。待原场景有自然启动时机，先核对交流供电、独占租约、正式组件和回退材料。用短窗口并校验实际余量。若要更换 KMD，先撤销永久许可，候选只使用一次性许可。正常结束后按已验收组件哈希回退，复核 Code 0、交流供电及许可状态。失联后先读实际启动与组件，再通过现有回退流程恢复。若出现超限、身份变化或未封口，保留回执并限定覆盖范围。长期开启的布防尚未验收。

自然发生重启后，在连接设备前用 `python3 tegra-x1-wddm/tools/recover_dma_receipts.py <控制端目录>/wire.jsonl` 读回独立日志，标出同一 DMA 最后已确认的步骤和第一个缺证据的步骤。再按既有连接规则核对新启动、系统事件、组件和恢复情况，写回开放故障。当前历史故障仍保持开放。
