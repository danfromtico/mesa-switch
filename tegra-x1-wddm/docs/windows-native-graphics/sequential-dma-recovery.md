# 旧式 SEQUENTIAL 首次 Present 的同包回执

使用旧式窗口正常出现时的短采集窗口。复用项目的 DxgKrnl ETW、GM20B DMA 诊断事件和独立控制端接收器。正式 KMD 能提供 Windows 侧时间线。KMD 入返及 GPU 围栏读回要使用已有的诊断候选 `ef790ec9`，该驱动曾在 94004 一次性许可下校准。每次以实际加载组件及其完整哈希为准。

## 同次提交的关联

| 步骤 | 证据 | 同包条件与覆盖 |
| --- | --- | --- |
| Windows 队列与调度 | DxgKrnl 178.1 入队和 175.1 提交 | 同启动、适配器 LUID、节点、上下文生命期，匹配 `hContext`、队列序号及对象 `pQueuePacket`。每个 `uliSubmissionId` 是一次独立的尝试。系统线程 PID/TID 是发事件的线程。DWM 所有权从设备与上下文取证。 |
| 选择提交分支 | DxgKrnl 105/106 的 5063 区间 | 只在同调度线程唯一包围 KMD 入返并排除相邻 175 时关联。函数编号单独出现时保留缺口。 |
| KMD 进入、准入及返回 | 项目 provider `c27c1f9b-62e8-4e21-b29b-6bb2d585c6d0` 的 7.2，阶段 1、2、5 | 用同启动的 Windows 433 建立 `hContext` 和私有 KMD 上下文的映射，再核对适配器、提交 fence、DMA 字节、提交线程和调用区间。阶段 5 记录实际返回状态。工作线程可能早于返回继续执行。 |
| 发布及 GPU 完成 | 7.2 阶段 3、4 | 阶段 3 观察到 GPFIFO 发布，实际 GPU 开始时刻仍缺直接事件。阶段 4 发生在命令完成字读回成功之后，可证实读回的 GPU 完成，完成的精确硬件时刻仍未知。 |
| Windows 收到驱动通知并处理完成 | DxgKrnl 177.1 和 176.0 | 分别读回通知与 Windows 的 DMA 完成处理。匹配上下文、同一次 DMA 完成号、队列序号、正常通知类型、无页故障及 `bPreempted=0`。驱动通知单独留下时，GPU 完成读回和退役各按其证据记录。 |
| Windows 队列退役 | DxgKrnl 180.1 | 180 的载荷没有 DMA 提交号。须以同一 178 的队列对象及队列序号、上下文生命期和唯一的非抢占 176 来归属。存在另一尝试或对象复用的歧义时保留未知。 |
| 系统结果 | 下一次启动的原始系统事件、启停时刻及已有恢复回执 | 记录实际启动和异常关机，首个异常或复位时刻只采用可独立定位的事件。 |

抢占后的 175 另开一条尝试。可回读的抢占完成按实际状态报告。即使几次尝试共用相同队列对象，完成号和回执也各自归属。DWM 信号、等待和后续呈现的选择事件按各自包记录。用应用日志或 DXGI 42/43 确定首次 Present 的线程和 QPC 范围。要把 DWM 包归到该窗口，还需同次窗口及组成链证据。

## 两个独立时钟与落盘

- 开始前在独立接收端保存本轮唯一标识、Windows 启动、系统与驱动组件哈希、进程、适配器、上下文映射及 QPC 频率。地址、序号和计数只在绑定的启动、捕获窗口和对象生命期内使用。现有实时流传输 175、5063、KMD 7、177、176 和 180。队列 178 与上下文 433 须另存同启动原始事件，现有实时流缺它们的独立落盘保证。
- 源事件的 QPC 与采集回调的 QPC 在同一 Windows 时间基准。独立控制端给每条收取和 `fsync` 返回写入本机单调钟和 UTC。Windows 收到 `ACK n` 后记录自己的 QPC。可用回调与 ACK 的顺序约束落盘位置。跨设备时点不直接相减。
- 接收器的 `wire.jsonl` 在控制端创建。保留原文件并在新进程用 [recover_dma_receipts.py](../../tools/recover_dma_receipts.py) 读取。单独的 EVENT 是已收取并可读回的记录，完整的 `fsynced` 是接收端完成前一条 EVENT 同步写入的记录，`PERSISTED` 是 Windows 收到 ACK 的回执。报告三者的计数及每个阶段的原始载荷。没有完整换行的尾记录保持未确认。格式错误的完整行会终止读取，已验证前缀仍可导出。
- 正常收尾时读回原生 ETW 停止状态、事件丢失、实时缓冲丢失和文件缓冲丢失。无 END 时最终丢失计数未知。即使收到带零丢失的 END，也同时核对上限、ACK、写入和传输错误。未知阶段可能发生在 ETW、回调、传输或落盘覆盖之外。

## 本轮准备状态

控制端恢复读取通过了真实进程中断的本地验证。回放的事件字节和源 QPC 来自 94004 的已有正常 DWM DMA，模拟的采集和 ACK 时钟单独标记。原场景和正常窗口均未重跑。现场尚未布防。

现有扩容实时收集器的上限为 8192 条，最长窗口 12 秒。旧版在桌面后台约一秒触达 4096 条，8192 版仅有本地压力验证。现有工具还需要同启动的队列和上下文原始回执。待原场景有自然启动时机，先核对交流供电、独占租约、正式组件和回退材料。用短窗口并校验实际余量。若要更换 KMD，先撤销永久许可，候选只使用一次性许可。正常结束后按已验收组件哈希回退，复核 Code 0、交流供电及许可状态。失联后先读实际启动与组件，再通过现有回退流程恢复。若出现超限、身份变化或未封口，保留回执并限定覆盖范围。长期开启的布防尚未验收。

自然发生重启后，在连接设备前用 `python3 tegra-x1-wddm/tools/recover_dma_receipts.py <控制端目录>/wire.jsonl` 读回独立日志，标出同一 DMA 最后已确认的步骤和第一个缺证据的步骤。再按既有连接规则核对新启动、系统事件、组件和恢复情况，写回开放故障。当前历史故障仍保持开放。

## 按 DMA 尝试持久化

ARM64 `dma_attempt_trace.c` 在同一个 ETW 会话捕获 Windows 调度、队列和上下文以及 KMD 7.2。随会话请求 29/32 rundown 和 433，用 29 中的所有者 PID 识别启动采集前已存在的 DWM 上下文。对新的应用上下文使用 27/30/433。178 的上下文、队列序号和对象与 175 的提交号一起形成尝试身份。DWM 包按所有者和上下文走匹配，字节长度从该包的 178 和 KMD 中分别核对。对照演练以首个 52 字节应用复制为应用侧验收对象，同轮保留合格的 DWM 普通队列。

控制端在每次收到并关联到尝试的阶段后，用 `dma_attempt_receiver.py` 提交一个完整前缀。每个前缀包含启动号、会话、适配器 LUID、上下文及生命期、队列身份、DMA 提交号、实际加载组件回执和原始绑定记录。前缀帧和确认帧分别有 SHA-256，先同步完整数据帧，再追加并同步绑定相同版本的确认帧，最后确认接收。完整包七个源步骤归入调度提交、KMD 入返、GPU 完成和 Windows 退役四段。现有 KMD 未提供独立 GPU 开始时刻。

同队列的重提必须见到前次 176 的抢占，再按新 DMA 提交号分别登记。180 归于此前按同提交号正常完成且仍属该队列的尝试。身份不唯一、计数不全或阶段乱序时保留已持久化前缀和缺口。可解析而无确认帧的末尾单列为待确认，部分写入或损坏帧之后不继续确认。接收目录和文件由独立控制端持有，Windows 侧 ETL 只作辅助材料。

控制端重读命令为 `python3 tegra-x1-wddm/tools/dma_attempt_capture.py <独立接收目录>/attempts.journal`。演练要求用受控回退重启获得新的正式启动号和组件回执，随后以全新读取进程仅读日志完成比对。清洁的采集末尾仍须核对实际 ETW 丢失计数和传输计数。缺 END 时最终丢失计数未知。已退休的合格应用包证明演练链路，DWM 事故覆盖根据同轮实际 rundown、队列和阶段另行判定。

## 原场景的布防边界

以原旧式 SEQUENTIAL 窗口的下一次自然启动为触发。沿用已存在的启动门控，在应用创建窗口及首次 Present 前开启独立接收端。当前签名收集器每次只运行一个 12 秒会话。窗口启动前的就绪条件是已提交 `capture_ready`，本次启动、正式或一次性候选身份及交流供电均已读回，且同次 rundown 看到目标 DWM 所有权、适配器和 433 关系。正式 KMD 下的观察限于 Windows 阶段。需要精确入返和 GPU 完成时，使用获准的一次性诊断候选。窗口按原使用方式启动一次。没有自然启动请求时仅保留独立监听。收集器等到实际门控消息才启动。若原应用已经越过启动门，则那次首帧处于未覆盖区间。

延用启动 94382 的实测预算。12 秒会话接收并确认了 1702 条，源事件最快一秒有 511 条，低于单会话 8192 条上限。独立包日志为 4,024,535 字节，应用退役事件到 Windows 收回控制端确认耗时 27.019 ms。这些是本轮短窗口计量。比确认更早发生的重启仍可能留下采集或落盘缺口。连续长期采集的容量、开销和覆盖尚无实测。

同轮 DWM 的 115 个关联尝试中，110 个完整退役。五个被抢占的前缀分别对应五个同队列、不同提交号的完整重提。分析目标是同启动 DWM PID 对应的设备、上下文和队列。为每次不同的提交号建立快照。若捕获终止、达到上限或失联，封存控制端当时已确认的前缀，保留未确认尾部。独占任务仅按原 SSH 间隔倒计时恢复连接，首失联后每 3 分钟一次，连续 30 分钟则暂停。候选恢复任务在约 14 分钟无本轮有效接触回执后回退，成功回连后先查实际启动、许可和已载组件。任何未经计划的重启单独写入故障表，另取系统原始事件定位首条异常，保留仍无证据的阶段。


## 门控及候选回退

启动 91476 的原入口是受控、一次性的 `board_local_cdd_controller.py` 发起路径。事故清理回执确认原 Windows 任务和应用目录均已删除。本轮为同样的六个签名文件或内容哈希、相同的旧式 SEQUENTIAL 参数恢复一个独立按需入口。具体任务和接收端进程见布防回执。主机的 `original_sequential_entry.py` 触发该任务。Windows 的同一 `Board-Case.ps1` 在创建原应用前写持久门控消息，独立接收端检测到后启动收集器，并等到已落盘的启动、适配器及 DWM rundown 后确认释放。按需入口没有全系统进程拦截。绕过入口直接启动 EXE 的活动不在本轮布防范围。

安装验收使用同一个主机派发函数及 Windows 任务，以自校验探针要求在收到独立 ACK 后退出。只有实际原场景请求才允许启动原应用和 ETW。试验候选只取得一次性许可，已使用的许可、实际加载组件、外接供电、捕获截止 QPC，以及受控恢复窗口都写入回执。收集器暂停或失联时不确认释放同一门控，也不自动重启同一次正常窗口。

候选试用超过既有时限时，受保护的 SYSTEM 恢复任务执行正式档回退。自动续行仅限于同一启动控制器拥有的回退阶段，先持久记录每一次受控重启请求，并检查交流供电。收集端 SSH 仍遵循 3 分钟间隔与连续 30 分钟暂停。恢复回执单独核对正式启动、许可、八个哈希和异常事件；人为计划的恢复时点和自然重启记录分别取证。

启动 94734 的待命窗口到期时没有收到原场景请求。原恢复任务以 `0x8007042B` 退出，Windows 仍处于 `CandidateActive`。控制端补启动了同一个所属恢复任务。Windows 随后记录两次计划恢复重启，经 94828 到达 94912。正式八件、Code 0、交流供电和永久许可均已核对，临时任务与目录已清理。System 在候选启动记录了约十秒的交流掉线。计划任务历史频道关闭，任务退出成因仍未知。恢复后读取的功耗模式为 `7`，本轮对照模式为 `1`，控制端未改写该设置。下次按需请求增加同一候选启动上的单次到期兜底，仅允许进入受保护的恢复逻辑。兜底目前只通过本地脚本解析。

候选窗口结束后，控制端的 `request_original_sequential.py` 保留同一个原诊断的按需入口。`--status` 根据本地互斥锁和最后请求的阶段标记，区分空闲、执行中、中断待恢复。明确收到下一次原场景请求后，`--start` 重新核对当前租约、交流供电、正式组件、发布清单以及可回退的 INF 和启动策略，并为该请求准备新的目录、启动与捕获身份。若正式组合更新，须先复核与该组合匹配的候选和回退材料。每个实际请求只安排一次试验。入口空闲时无常驻接收器、SSH 或驱动切换。其他日常游戏在这个入口的覆盖范围之外。

控制端补救恢复正式 GPU 后，在同一启动 94912 上将功耗模式从固定档 7 恢复为手持档 1。30.6 秒后复核时，DWM 1380、Code 0、八项正式组件、五项实载及 85% 充电上限均与恢复前一致。模式 7 的来源仍未知。[手持恢复回执](handheld-94912-restored.json)

下一次真实请求使用控制端 `seq-dma-natural/request_original_sequential_v2.py`。接收器结束后，入口先以新进程读取本次请求的 `live/attempts.journal`，在控制端保存 `capture-readback.json`，然后才通过 SSH 收取 Windows 原件和检查恢复状态。回执记录源文件 SHA-256、已确认的提交前缀和未确认尾部。无日志或读回失败时单独记录，继续设备恢复。此顺序已用归档实机数据和本地断线替身核对；新版入口尚无新的实机请求。[离线断线回读复核](on-demand-prefix-recovery.json)
